# Human calling modernization

This document tracks the PostgreSQL human-calling implementation. It is not a claim of PBX commissioning or production readiness. Campaign dialing remains a separate workflow documented in `issabel-dialer.md`.

## Current evidence and transport contract

The existing `src/integrations.js:originate` requests an extension channel, then a destination in the configured context, with asynchronous AMI submission. It now uses the shared authenticated AMI session and closes the connection after the correlated action response; its compatibility wrapper discards lifecycle events and continues to report submission only. Its result establishes submission only; the PostgreSQL platform currently has manual call logs and wrap-up, not a connected two-leg outbound lifecycle.

Asterisk documents the requested channel, destination context/extension/priority, asynchronous origination and explicit channel correlation IDs in its [AMI Originate reference](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Actions/Originate/). Its separate [OriginateResponse event](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Events/OriginateResponse/) is not a substitute for identifying customer-leg answer and terminal events. These current upstream references are design evidence, not verification of an installed Issabel/Asterisk version. No legacy infrastructure was contacted.

## PostgreSQL authorization and preferences

Migration 049 stores calling profiles, extension identities, explicit extension-user grants and private preferences. A profile identifies server-side configuration by an immutable `server_key`; it holds the channel driver, dedicated manual context, international destination prefixes and duration limit. It does not store an AMI/SIP password. The server-side runtime resolver matches that key to the explicit deployment registry described below. Profile activity means administratively enabled, not connected or commissioned. Context syntax checks cannot prove the actual PBX dialplan enforces the destination policy.

Extension identities are unique within a profile and preserve leading zeros. Changing an extension number or server identity requires a separate record; retirement preserves existing references. Explicit user grants authorize extension selection. The legacy `users.extension` field alone gives no calling authorization and is not silently imported. More than one user may be authorized for an extension; the durable call-reservation layer prevents simultaneous use.

Administrators need global `calls.admin`. Profile/extension/grant changes require a reason and reviewed revision, use the exclusive policy transaction boundary and append audit events atomically. Self-service settings require `calls.settings`; the actor can select only an active extension with an active explicit grant and active profile. Selection is rechecked before replaying a saved preference request. Competing initial writes use revision 0 and serialize on the user row; the loser receives a revision conflict. Clearing a preference remains possible after its extension becomes unavailable.

Preferences distinguish `extension_first` from `browser`. They are preferences, not executable call requests. Current readiness always reports `can_call: false`, with selection, configuration, unconnected transport or unimplemented browser-mode reasons described below. Own-settings responses contain authorized extension numbers and profile labels, not server configuration. No SIP credentials are returned or persisted in browser storage.

Administrator detail reads include inactive profiles/extensions and current revisions. The dedicated user selector requires global `calls.admin` without unrelated identity administration; it returns only active user IDs, localized names and active status, in pages of 50 with a separately validated retained selection. Existing grants continue to expose inactive users for explicit revocation. The bilingual administrator UI is described below.

## Server deployment registry

`COLLECTIONS_CALLING_SERVERS` is a JSON array of at most 32 explicit server entries (maximum 64 KiB). Each entry has `key`, `host`, `username_env`, `secret_env`, `contexts`, `channel_drivers` and `destination_prefixes`; an explicit `calling_windows` policy is required for calling configuration readiness. Optional fields are `port`, `tls`, `server_name` and `max_call_seconds`. Credential references must begin with `COLLECTIONS_PBX_`. Unknown fields, duplicate keys, unsafe contexts, malformed endpoints/policies and remote plaintext configuration are rejected with a fixed error that does not quote values. The resolver never reads legacy configuration or falls back to `ISSABEL_*`.

TLS is the default, with port 5039. Explicit plaintext uses port 5038 by default and is restricted to literal loopback addresses for a separately managed local tunnel. An optional TLS server name must be a DNS name. Credentials are held in a startup snapshot on the server and reject empty/control-character values. Update the protected deployment environment and restart the runtime to rotate them. Do not enter credentials into profiles, URLs, browser storage, audit reasons or source control. `.env.example` documents a synthetic configuration.

The configured profile context and driver must be allowed by the deployment entry. Every profile prefix must narrow an allowed server prefix, and its duration cannot exceed the deployment limit (default 3,600 seconds). Missing servers, unavailable credentials and policy mismatches return fixed status codes. The admin detail API returns only `configured`, `can_call` and `reason` under `configuration`; personal preferences expose only the reason after validating the active extension grant. Runtime hosts and credential references/values are never returned by these APIs.

This validation opens no socket, checks no installed dialplan and establishes no PBX connectivity. A matching configuration with an open calling window still reports `transport_not_connected` and `can_call: false`; a closed window reports `calling_window_closed`, and missing schedule configuration reports `calling_windows_missing`. Browser mode still reports `browser_not_implemented`. Profile activation does not certify deployment or transport readiness.

## Durable attempt preparation and recovery (internal service)

Migration 050 introduces `human_call_attempts` and immutable transition events. The internal attempt service accepts explicitly confirmed extension-first intent with reviewed case, contact, extension, profile and grant revisions. It validates current placement/contact scopes, case/portfolio availability, do-not-call and closed flags, approved outstanding balance, active unblocked phone/mobile contact, international number syntax and runtime prefix policy. Destination and extension numbers are server-resolved immutable snapshots. A non-secret deployment-policy fingerprint detects changed endpoints or routing policy before dispatch; credentials are not stored in attempts.

Partial unique indexes reserve one active attempt per agent, extension and case. Preparation is audited and idempotent; permission and review validation precede replay. An owner can cancel only a never-dispatched prepared intent, using its reviewed revision and a reason. Cancellation does not require retaining case placement scope, so lost placement permission does not prevent safely cancelling an unsent intent.

The internal worker claim rechecks eligibility, commits a unique dispatch token and moves to `dispatching` exactly once. A retry cannot retrieve a previous token. Prepared intent expires after 60 seconds. Recovery handles at most 50 rows with locked-row skipping: expired prepared intent becomes `expired` and releases reservations; an expired 30-second dispatch lease becomes `uncertain` and retains all reservations. Transition events and audit commit atomically. Recovery works even if the original actor is inactive.

This service has internal AMI owner/transport integration but no HTTP call-submission endpoint or executable worker yet. The internal leg-evidence layer below can establish awaiting-wrap-up state, but has no reservation-release shortcut. Real bridge/auxiliary correlation, authoritative topology/rejection proof, worker discovery/recovery, active-call mutation guards and calling-workspace integration are still required before enabling calls. No elapsed timeout proves a remote call ended.

## Durable PBX leg evidence (internal adapter boundary)

Migration 051 stores normalized, immutable PBX evidence with per-profile event identity and immutable per-profile channel-to-attempt bindings. The internal ingress requires the exact durable dispatch token. It accepts channel creation/ringing/answer/hangup, a verified agent/customer bridge and an authoritative closed channel manifest. It rejects raw AMI payload fields. The adapter must supply stable event and channel identities that include PBX instance/boot identity where necessary, timezone-qualified occurrence timestamps, verified attempt correlation and correct agent/customer/auxiliary classification. These requirements are not yet implemented by a live adapter.

Asterisk describes [Hangup](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Events/Hangup/) as a channel event carrying Uniqueid and Linkedid, and documents [BridgeEnter](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Events/BridgeEnter/) separately from [OriginateResponse](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Events/OriginateResponse/). Our normalized `bridge_connected` event requires adapter evidence that the authorized agent and customer share the intended bridge; an agent answer or Originate response alone is insufficient. The upstream references do not verify the installed Issabel/Asterisk version.

Projection uses immutable occurrence evidence, not arrival order. Channel creation or hangup alone does not claim ringing; answer does not claim a connected bridge. A nonempty closed manifest must account for exactly all observed channels, include the agent leg and have terminal hangup evidence for each channel at or before closure. The manifest is an adapter assertion based on authoritative topology completion, not merely a list of channels observed so far. Out-of-order known evidence may complete a pending manifest. Conflicting roles, unaccounted channels, inconsistent manifests or activity after terminal evidence produce uncertainty.

Completion moves only to `awaiting_wrapup`, which still reserves agent, extension and case. Late contradictory evidence moves it to `uncertain` while retaining reservations. Evidence can reconcile a lost dispatch lease even if its original actor has been disabled; ingestion is a trusted internal operation, not an actor-authorized write endpoint. Exact duplicate events return current projection without incrementing revision or renewing the lease. Reused event/channel identities cannot bind to another attempt. Evidence never renews the observation lease. New nonterminal evidence received after lease expiry preserves its phase facts but moves dispatching state to uncertain; the authenticated owner heartbeat performs the separate renewal. Authoritative completion may still reconcile uncertainty.

Evidence, bindings, projection and audit commit atomically. Scoped evidence reads use 100-row forward cursor pages. Input permits at most 64 manifest channels and a stream is bounded at 10,000 events; the latter limit requires operator reconciliation rather than accepting unbounded input. The current implementation reprojects the bounded stream per event; large-load sizing/optimization is not established. HTTP submission, live event correlation, topology closure/rejection proof, worker integration and live commissioning remain incomplete. Calling-workspace wrap-up is connected as described below.


## Reviewed live-call wrap-up and late-evidence holds

Migration 052 links a `human_live` call record uniquely to its attempt. The internal wrap-up service requires current call-log and call-read scope, an available case, reviewed case/attempt revisions and complete non-conflicting termination evidence. It reuses the ordinary reviewed disposition implementation. Call record, disposition, optional explicitly agreed promise, callback, case revision/status, audit and attempt completion commit atomically. Only that completed transition releases the reservation indexes. Idempotent replay cannot create a second call, outcome or promise. Live duration remains null until authoritative duration evidence is integrated; existing manual/import duration constraints are preserved. Original live-call identity cannot be edited.

Call preparation, claim, cancellation, evidence, recovery and wrap-up now acquire the same sorted agent/extension/case advisory locks before attempt/case row locks. Recovery tries those locks without waiting and skips busy resources. This ordering avoids call-specific reservation-versus-row-lock cycles and serializes late evidence with preparation/dispatch.

Valid late evidence is still recorded after wrap-up. If it contradicts the completed topology, the reviewed call remains completed and unchanged, but a sticky safety hold blocks any new preparation or prepared dispatch sharing its agent, extension or case. This works even when a newer attempt already holds a reservation, without trying to reopen an old unique-index reservation. Exhausting the evidence stream limit similarly places a safety hold and returns `accepted:false,code:calling_evidence_limit`; repeated capacity failures do not keep incrementing revision. Holds are not cleared by retries, preference changes or expiry. Explicit evidence-based hold resolution and stopping an already-dispatched remote call remain future reconciliation/transport work.

The call-activity workspace below connects reviewed wrap-up to HTTP/UI; no live transport is enabled. Existing manual logging and transcript-import workflows continue to use their current endpoints. The workspace surfaces awaiting-wrap-up attempts, unknown duration and safety holds. Outbound calling and reconciliation actions are still required for the full calling workflow.


## Call activity workspace

The bilingual `#call-attempts` page is linked under `calls.read`. It lists all scoped attempts in searchable 50-row pages with active, awaiting-outcome, completed and safety-hold filters. Detail and evidence-cursor routes survive reload. Current call scope controls metadata; current independent contact scope controls the recorded destination. Evidence history pages forward at 100 rows without discarding the reviewed outcome draft.

The outcome form records notes, optional Riyadh-time callback and an optional explicitly agreed promise. It retains drafts through language changes and evidence paging, resets private drafts on actor changes and blocks save when case or attempt revisions changed. Reload/discard is explicit. Success shows the saved disposition/callback and linked call; unknown duration remains explicit. Loading clears stale detail content, and detached responses cannot replace current activity. No dispatch token or raw AMI data reaches the browser. These controls do not originate calls, stop a dispatched call or clear a safety hold.


## Cancelling unsent intent

The call-activity detail exposes cancellation only for the prepared intent owner under current `calls.settings`. Its reason and reviewed attempt revision are submitted explicitly, with a stable retry key. The draft reason survives language changes and resets across actors/navigation. Changed revision or permission blocks submission until explicit reload; a failed cancellation re-reads current state so dispatched intent no longer presents the unsent-cancellation form. Saved cancellation survives reload and creates no completed-call record. This action is distinct from hanging up a dispatched call or clearing a safety hold. An unsent intent may still be cancelled after losing placement permission or when its case becomes locked; current settings permission remains required.


## Persistent AMI transport wire boundary

`src/platform/ami-protocol.js` supplies the internal streaming decoder and action encoder for the forthcoming persistent transport. The [official AMI specification](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-Manager-Interface-AMI/AMI-v2-Specification/) defines CRLF framing, case-insensitive keys and ordered repeated fields. The decoder requires a manager greeting, preserves repeated fields and Unicode values across arbitrary byte boundaries, and rejects ambiguous singleton routing fields. Transport consumers must use `amiSingle` for channel/correlation identifiers rather than selecting an arbitrary duplicate. Empty values with no trailing space are accepted, matching Asterisk's documented examples.

Messages are limited to 64 KiB, lines to 8 KiB, fields to 256 and a supplied chunk to 1 MiB. Malformed framing, invalid UTF-8, capacity violations and truncated termination poison the decoder. Errors contain fixed text, without frame values. Outbound actions require one Action and ActionID, preserve ordered variables and reject injected controls or competing routing fields. The codec opens no connection, authenticates no session and does not normalize events into call evidence. Persistent socket/session management, restricted action selection, timeouts, heartbeat, reconnect uncertainty, topology proof and hold reconciliation remain required.


## Persistent authenticated AMI session

`src/platform/ami-session.js:connectAmiSession` now consumes server-resolved connection settings. It uses certificate/hostname-verified TLS 1.2 or newer, or explicit literal-loopback plaintext for a separately managed tunnel. It waits for the manager greeting before sending credentials. [Login](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Actions/Login/) requests `Events: on`; a matching success response establishes the session. This does not verify the account's event privileges, PBX version, dialplan, media or calling readiness.

Each action receives a unique connection-prefixed ActionID and a separate response promise. Unknown or duplicate replies cannot settle another request. Events are routed independently, including `OriginateResponse` events that themselves contain a `Response` field. Ordered event consumption is asynchronous and bounded at 256 pending/in-progress events; overflow, consumer failure or a stalled consumer closes the session. Session IDs identify connections only: they are not PBX boot identities and must not substitute for durable event/channel identities during reconnect reconciliation.

The internal action allowlist includes Ping, Originate, Hangup, CoreStatus, CoreShowChannels, BridgeInfo, Getvar and Status. The future dispatch owner must still construct restricted actions from current authorized intent; this low-level module does not authorize destinations or expose an HTTP command API. At most 64 commands are pending. Writable backpressure rejects additional submissions without retry. Defaults are five-second connection/authentication, action and event-consumer deadlines. A correlated [Ping](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Actions/Ping/) with Pong is required every ten seconds after the previous heartbeat completes. Heartbeat success proves session responsiveness only, not call termination or gap-free event evidence.

Disconnect, malformed input, lost acknowledgements and queue/consumer failures reject outstanding actions and resolve the `closed` notification with a fixed code. No command is replayed or connection reopened automatically. Remote error text, endpoint details and credentials are excluded from session failure messages; raw response/event frames are internal and must not be returned by HTTP handlers. Deliberate close also notifies the owner. No client-side navigation or socket timeout releases a call reservation.

`createCallAttemptService.observationLost` is the internal durable counterpart for the future transport owner. It requires the exact dispatch token and a fixed loss-reason code, atomically transitions dispatching to uncertain, and records transition plus reason audit even if the actor is inactive. Duplicate reports do not increment revision or duplicate history. It leaves already-established awaiting-wrap-up/completed states intact and releases no reservation. A race with authoritative closed topology can still establish awaiting-wrap-up; the reviewed outcome remains required for release. Audit failure rolls back the transition and must be retried by the owner while ordinary expiry recovery remains available.

These modules are not yet wired to the application worker, runtime readiness or HTTP preparation/dispatch. Persistent session ownership, current eligibility at send, observation renewal, stable PBX identity/correlation, dialplan-enforced duration/destination restrictions, topology/rejection reconciliation and both calling modes remain open. The existing `src/integrations.js:originate` compatibility wrapper now uses this shared session and retains its submission-only result. It closes after the action acknowledgement and does not record lifecycle events. Its unencrypted connection is now restricted to literal loopback tunnels; remote deployments require trusted TLS. The campaign-specific lifecycle adapter remains separate and still requires PostgreSQL migration/integration.


## One-shot final dispatch authorization

`createCallAttemptService.dispatch(actorId, attemptId, submit)` is the internal boundary for a future connected transport owner. The owner must authenticate the appropriate session before calling it. Dispatch first uses the existing irreversible claim and commits its token. It then opens a fresh actor/policy transaction, takes the common sorted resource and case locks, verifies that the claim is still dispatching and rechecks case/contact eligibility, ownership/grants, approved balance and the recorded deployment fingerprint. A changed or revoked condition after claim prevents submission.

The final transaction records send authorization before invoking the transport. After potentially waiting for validation/audit locks, it checks both the original prepared-intent deadline and the dispatch lease against PostgreSQL `clock_timestamp()`, subtracting the query's monotonic elapsed time conservatively. An expired click cannot become a new call through a slow authorization path. The synchronous callback receives frozen server-resolved attempt/routing snapshots and must enqueue exactly one restricted AMI action, returning the shared session's `{actionId, result}` handle. It must not reconnect, retry or await a network response inside the transaction. This is a trusted internal callback, not a user-extensible API.

Policy and case locks remain held through synchronous enqueue, so a concurrent application permission change cannot commit ahead of the final authorized enqueue. PBX acknowledgements are awaited by the owner afterward; successful enqueue or authorization audit is not proof of remote acceptance, answer or termination. If audit fails before enqueue, no callback runs. If submission/receipt validation or the transaction fails after the durable claim, observation loss records `dispatch_failed` and retains uncertainty. This includes a rollback after bytes may already have been queued. Calling dispatch again must claim again and is denied; it cannot replay the old token or resend an uncertain attempt. If recording loss also fails, the operation returns a reconciliation-required error and the durable lease remains for recovery.

The callback's acknowledgement promise is observed immediately to avoid an unhandled rejection if commit fails, but its original success/failure remains available to a successful caller. The owner still needs to report subsequent acknowledgement/session failure, ingest authenticated evidence, maintain observation and perform reconciliation. The send method is not exposed over HTTP and does not yet constitute a connected calling worker. Calling windows are enforced as described below. Dedicated dialplan limits, live mutation/stop guards and the other outstanding calling requirements must be integrated before enabling placement.


## Explicit deployment calling windows

Each PostgreSQL `COLLECTIONS_CALLING_SERVERS` entry must declare `calling_windows` before it can resolve for placement. There is no implicit unrestricted schedule. Missing configuration produces `calling_windows_missing`; an explicit empty array is a valid closed-all-week policy. Schedules contain at most 32 objects with exactly `days`, `start` and `end`. Days are unique integers 0 (Sunday) through 6 (Saturday). Times use `HH:mm` in `Asia/Riyadh`, with inclusive starts and exclusive ends. `24:00` is accepted only as an end; equal start/end values are rejected. An overnight range belongs to its starting day. Overlapping/adjacent ranges form a canonical union, including continuity across the weekly boundary. An explicitly configured full-week union has no schedule closing deadline.

For example, `[{"days":[0,1,2,3,4],"start":"09:00","end":"17:00"}]` expresses one organization-chosen weekly policy. This is an illustrative deployment configuration, not a legal or organizational default. Use the organization's approved hours. API/worker restart applies protected deployment changes; browser administrators cannot override this policy through profile fields or call input. The canonical schedule joins the reviewed deployment fingerprint, so narrowing/changing allowed time invalidates existing reviewed intent even when the current instant is still allowed; equivalent unions do not create artificial policy changes. Existing prepared intents from before schedule fingerprinting must expire or be cancelled and reviewed again.

Preparation and claim check PostgreSQL `clock_timestamp()` against the schedule. Final dispatch checks it again after authorization/audit waits and subtracts the query's monotonic transit time, so a window closing before enqueue prevents submission and retains the claimed attempt as uncertain. Settings/readiness status is advisory server-clock information; actual placement uses database time. Status never changes `can_call` to true while transport integration remains incomplete. The personal and administration screens distinguish missing configuration from a closed Riyadh window in English and Arabic without disclosing credentials.

Windows restrict new origination. They do not prevent cancelling an unsent intent, ingesting evidence, recording observation loss or saving an authorized wrap-up; window closure does not prove an active call ended. The synthetic browser fixture deliberately has a closed API schedule while retaining previously prepared/ended attempts to verify these completion/cancellation paths. This policy applies to the PostgreSQL human-calling service; existing SQLite/campaign configuration remains separate until its explicit migration. PBX-side restricted routing and browser SIP enforcement remain required, so this checkpoint does not enable placement or claim live commissioning.


## Restricted extension-first AMI submission

The private worker preflight `transportConfiguration(actorId, attemptId)` verifies current ownership, prepared state/expiry and the same placement/contact/profile/window eligibility before returning a frozen connection configuration. It neither opens a socket nor consumes the claim. This credential-bearing result is internal only and has no HTTP route. A connection made afterward still receives all fresh checks in final dispatch.

`dispatchOnSession` connects the one-shot database boundary to `extension-first-action.js`. It accepts an authenticated shared AMI session, not raw routing fields. Sessions retain an immutable private snapshot of endpoint, TLS/server-name and authentication values; `matchesConnection` compares the final resolved configuration and returns only a boolean. A wrong or closed session cannot enqueue Originate, and a post-claim mismatch retains uncertainty. Mutating the object originally supplied to the session cannot change its binding. Sessions expose no credential-bearing configuration property.

The action rings `PJSIP/<authorized extension>` or `SIP/<authorized extension>` first, using the server-resolved dedicated context and international destination at priority 1 with asynchronous origination and a 30-second agent-answer timeout. It supplies `ChannelId=hc-<dispatch token>`, which is stable for that durable claim, plus inherited `COLLECTIONS_HUMAN_ATTEMPT`, `COLLECTIONS_HUMAN_TOKEN`, `COLLECTIONS_HUMAN_DESTINATION`, `COLLECTIONS_HUMAN_EXTENSION` and `COLLECTIONS_HUMAN_LIMIT` variables for the forthcoming restricted dialplan/event contract. No arbitrary caller ID, application/data command, Local channel or second-local-channel ID is accepted. The [Asterisk Originate reference](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Actions/Originate/) documents the action fields and distinguishes answer timeout from channel variables; version-specific support still requires commissioning.

The supplied maximum-duration variable is policy input for the restricted dialplan, not proof of enforced call duration. No dialplan is installed or remote PBX configured by this helper. Agent-channel correlation does not yet supply customer/auxiliary topology or stable identities for PBX-created channels. The connected owner must retain the session, normalize correlated events, report observation loss, enforce stop/observation deadlines and reconcile before release. A successful action acknowledgement leaves the attempt dispatching/pending; it creates no answered/completed-call record.

Synthetic acceptance traverses private preflight, a real loopback AMI login, PostgreSQL claim/final authorization and exactly one received Originate across competing dispatches. It also proves wrong-authentication session refusal with zero Originate actions. These are internal socket/service checks, not a running dedicated telephony worker, browser placement or a commissioned PBX route.


## Long-lived internal call owner and observation renewal

`createHumanCallOwner` in `human-call-owner.js` now manages the existing preflight/session/dispatch path independently of heavy report/import queues. It reserves local ownership before asynchronous connection work, bounds concurrent ownership (32 by default, configurable up to 64), and relies on the committed database claim to prevent dispatch by another owner/process. It retains the session after acknowledgement and returns a separate closed notification. Duplicate/capacity requests are rejected; there is no automatic origination or reconnection retry.

The factory requires a trusted `consumeEvent` adapter. It passes the immutable claimed attempt, connection session ID and raw frame to that adapter in session order. There is no default consumer that silently discards claimed-call evidence. The adapter still must verify attempt/channel correlation and normalize/persist evidence; merely receiving a frame does not make it authoritative call state. Events received before the intent is dispatched do not belong to that new attempt. An acknowledgement remains submission-only and creates no completed call.

The AMI session can now deliver an internal `onHeartbeat` notification after a correlated Pong and after earlier queued evidence is consumed. Renewal callbacks share the bounded ordered consumer queue, deadline and failure behavior. `renewObservation` requires the dispatch token and a still-live dispatching lease. PostgreSQL rechecks expiry at the renewal update; successful renewal extends observation by 30 seconds without changing business revision, phase or outcome and without appending an audit row for every heartbeat. Expired or held observation becomes uncertain with one transition and a reasoned `observation_unavailable` audit. Existing uncertain/awaiting-wrap-up/completed attempts are not revived. The operation works for inactive actors because it observes already-dispatched work rather than authorizing new contact.

The owner reports session/consumer loss and deliberate shutdown through `observationLost`. Stop/shutdown closes observation; it does not hang up a remote call or cancel a prepared intent. A connection finishing during shutdown is closed without dispatch. The owner waits for in-flight dispatch bookkeeping before reporting loss so a token created during shutdown is not omitted. Repeated shutdown paths share one completion operation. A closed result reports `persistence:recorded` when the database processed the loss notification, `not_required` when dispatch never began, or `recovery_required` when durable status could not be confirmed. Loss-persistence failure is not reported as success; the caller must drive durable recovery. Owner startup failure also carries a `recovery_required` flag without exposing remote/private error text.

An owner remains registered until stopped or its session fails; it does not infer quiescence from a single terminal-looking event. The eventual worker/correlation adapter must decide when observation can be retired, handle closed notifications/recovery, enforce remote stopping/max-duration policy and reconcile late/unknown topology. The module is tested through synthetic AMI sockets and PostgreSQL, but is not yet wired to an executable telephony worker or placement HTTP/UI. PBX normalization/dialplan enforcement, authoritative reconciliation and browser SIP remain required before enabling human calling.

## Native agent-leg evidence

`ami-agent-evidence.js` adds an internal component for the owner's authenticated event consumer. It accepts `Newchannel`, `Newstate` and `Hangup` only when `Uniqueid` exactly matches the app-issued `hc-<dispatch token>` channel ID. Matching a phone number, channel name or `Linkedid` is insufficient. This ID belongs to a unique application claim and does not depend on the AMI connection session; native PBX-created customer IDs still need stable PBX boot identity and verified association.

The component requires the PBX `Timestamp` header in seconds with six fractional digits. Enable `timestampevents=yes` in the commissioned manager configuration; the [Asterisk 20 manager implementation](https://github.com/asterisk/asterisk/blob/20/main/manager.c) emits that header when enabled. It never substitutes receipt time. Evidence identity hashes the attempt, agent channel, event type, exact microsecond timestamp and normalized kind, so reconnecting/reordered headers do not change identity. Domain occurrence time remains millisecond precision, while new evidence also preserves source microseconds for bridge ordering. Historical rows are not rewritten.

Numeric state and description must agree. Ring/Ringing supplies agent ringing, Up supplies agent answer, and creation can carry both channel creation and its explicit state. Other recognized states supply no invented business outcome. The [Newstate contract](https://docs.asterisk.org/Latest_API/API_Documentation/AMI_Events/Newstate/) describes the state/identity fields. A real Hangup supplies only that channel's hangup. OriginateResponse, hangup requests and DialBegin supply no agent evidence through this component. BridgeEnter/BridgeLeave now supply typed membership evidence as described below; they do not independently establish a customer role or closed topology.

The consumer awaits each durable evidence write, relies on the existing transactional deduplication/projection, and propagates persistence or evidence-limit failure into the owner's observation-loss path. Raw frames and caller details are not persisted. Ambiguous correlated headers, contradictory states and missing/invalid PBX time fail consumption. It remains a component, not the default complete consumer: customer/auxiliary association, actual bridge evidence, topology closure, reconciliation and executable worker integration remain required.

## PBX process epoch and native identities

The authenticated owner and direct `dispatchOnSession` path now require `Getvar` for the fixed global `COLLECTIONS_HUMAN_PBX_EPOCH` before claiming a call. The response must contain one matching Variable, one Success response and one canonical UUID v4 Value. Missing, malformed, denied or changed identity closes the session with a fixed error. ## Dedicated calling maintenance process

## Native hangup diagnostics and closure evidence

Lease recovery now uses its own attempt-ID cursor, independent of the bridge journal cursor. ### Precise terminal channel ordering

The channel projection compares native `source_micros` using integer microseconds, including last activity against hangup and hangup against the declared topology-completion time. A later hangup cannot erase an earlier terminal contradiction. Native activity one microsecond after hangup invalidates completion even when both timestamps render as the same millisecond. Existing normalized evidence without a precise source retains its declared millisecond boundary; it is not rounded forward to cover later native hangups.
