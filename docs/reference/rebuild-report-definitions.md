This is an incremental behavior contract. Unlisted variants in LEGACY_PARITY.md remain open. Source inspection is read-only; no legacy runtime or infrastructure was contacted.

## Collections: RPT-06, RPT-07 and RPT-08

Sources: `old/CAWP-API/app.py` functions `getPayments/exportPayments`, `getPaymentsByUser/exportPaymentsByUser`, `getPaymentsApprovalStatus/exportPaymentsApprovalStatus`, and `srverSideMode/exportServerSideMode`. Frontend tables: `views/collections/users/list/PortfoliosTable.tsx`, `views/collections/currentUser/list/PortfoliosTable.tsx`, and `views/accounts/list/PortfoliosTable.tsx` under the old frontend.

| Variant | Actual legacy inclusion | Target inclusion |
|---|---|---|
| RPT-06 General collections | Payment date interval; all approval states; creator branch filter; supervisor users OR supervised contracts | Current report/case scope; all statuses unless explicitly filtered; creator branch preserved independently of contract branch |
| RPT-07 My approved collections | Current user is payment creator; approval_status=True; payment date interval | Current scope AND creator=current actor AND status=approved |
| RPT-08 Approved collections | Same supervisor/contract rules as general collections, but approval_status=True | Current scope AND status=approved; **not** the pending approval desk |

Legacy date filtering uses `between` on timestamp-valued payment_date with client-supplied start/end. The target stores a business payment date and accepts inclusive YYYY-MM-DD dates, deliberately avoiding a midnight upper-bound omission. Legacy timestamps require explicit Riyadh conversion during migration; this report implementation does not resolve ambiguous source timestamp/money meanings.

The legacy tables expose: creator, amount, payment date, creation date, account, contract, customer, identity number, original debt, collection method/type, approval date/actor and (in general collections) approval comment. The target preserves these fields, adds portfolio and explicit payment status, and uses integer halala with exact decimal export formatting. Original debt is repeated per payment row and must not be summed as recovered funds.

RPT-07/RPT-08 return totalAmount over the filtered rows before pagination. RPT-06 currently returns row count without that total. The target exposes unambiguous recorded/approved/pending/rejected/reversed amounts and counts for every variant. Recorded amount is not recovery. Reversed payments retain their historical receipt and approval fields but contribute zero to current approved recovery.

Authorization correction: legacy historical payment creator/team relationships can expose records after case reassignment. Current permission scope is authoritative in the target, so report inclusion intersects current case scope. Creator/branch filters narrow that scope; they never restore removed access. This is an intentional authorization correction, not a claim that legacy access controls were equivalent.

Legacy generic filters/sorts are dynamic and include inconsistent nested accessor spellings. Target filters and sort keys are explicit and validated; full parity of every generic filter operator remains open until individually mapped and tested. Preview/export must use the same normalized definition and SQL builder. Report variants are not closed by a preview alone: private asynchronous export, current download authorization, exact totals, date boundaries and browser checks are required.

## Implemented payment-report path

`src/platform/report-definitions.js` normalizes definitions/filters and builds the shared scoped query. `reports.js` previews 100 rows per page with full filtered totals in one statement snapshot. SQL sorts have stable payment-ID tie breakers; query text is literal rather than a wildcard expression. The API also supports explicit creator, creator-branch, contract and portfolio filters. The UI now exposes searchable, paginated selectors for all four fields in addition to variant, status, inclusive dates, text query and sorting. Remaining legacy generic filter operators still need individual parity mapping.

`POST /api/reports/:kind/exports` accepts a normalized definition under an idempotency key and commits a private report run plus durable job/outbox before returning 202. The heavy worker uses a repeatable-read cursor in batches of 500; it does not build the entire spreadsheet in HTTP memory. Generation takes a **new snapshot**, so a later export need not equal an earlier preview if data changed. Its metadata records normalized filters, requested time, generation cutoff, row count, exact totals (halala), actor and currency. Export intersects read and export scopes; a user with broader read permission can therefore export fewer rows than the preview shows, as stated in the UI. CSV monetary columns explicitly use `_sar` and exact decimal strings; text cells are formula-escaped, UTF-8, with English field names and both language values where stored.

Each attempt records the distinct cases actually included. It rechecks `reports.read` and `reports.export` at batch boundaries and publication; jobs, retries and downloads reauthorize the recorded cases against current scope. Reassignment cannot become invisible by changing dates/statuses so that a rerun would omit the case. Artifacts are submitter-private, expire after seven days, are capped at 100 MB, and failed/unpublished files are removed. Durable job leases, attempt history, outbox recovery and cancellation are shared with imports. Report generation is read-only with respect to case/payment data. Physical deletion of expired published artifacts remains a shared retention task.

Evidence: PostgreSQL tests cover approved-only/current-creator rules, date endpoints, exact status totals, 105-row pagination, literal search, current case scope, durable acceptance during broker outage, duplicate requests/delivery, CSV formula escaping/bilingual values, 1,001-row stable-snapshot export during concurrent inserts, cancellation/reassignment cleanup and a real BullMQ report worker. Manual Chrome verified the synthetic English general report, exact SAR 200.01 recovery, export job completion and browser download; Arabic approved-only selection disabled incompatible statuses and rendered the same amount. An RTL screenshot was inspected, not saved. This closes the preview/background-export path for these definitions, not all report parity or remaining filter/UI work.

### Atomic note and current follow-up workflow

A user may optionally select a future time while writing a plain or classified note. The API requires both current `activities.create` and `cases.update` scope, current case revision and writable case availability; closed and do-not-call cases reject scheduling. It atomically saves the immutable note's `next_contact_at`, updates `cases.next_at` and revision, records audit metadata including the previous current follow-up, and invalidates scoped aggregates. Duplicate replay rechecks current permissions, while competing schedules reject stale revisions. An empty time preserves the existing callback; ordinary notes retain their prior permission/revision contract. This creates neither payment nor promise evidence.

Before: the target required entering and saving a note, then entering and separately saving case follow-up (two writes). After: enter note, optionally select time, save once (one atomic write), remaining in the same case. The preserved time appears on the note timeline and in RPT-16. Subsequent independent rescheduling does not rewrite that historical note. Browser date/time input uses the workstation's displayed local time and sends an explicit ISO timezone; reports apply Riyadh calendar dates.
